# TLC v0.0.8 — the shared plane

v0.0.8 is the first build that can reach another phone. The private record is still local,
non-custodial and readable without a server. What is new is a **consented shared plane**: a thin,
self-hostable relay for encrypted one-to-one messages and live presence, plus a companion
Pear/Holepunch node for record handoffs.

## What is live

- **A real relay.** The app can join a live relay over HTTPS/WSS, register a handle and its public
  keys, and open an authenticated stream. The canonical relay is operated by OriginLabs1; the
  address is build configuration, so a circle can deploy the same source and point a build at their
  own relay. The relay source is in [`relay/`](../relay/) and deploys with one `wrangler deploy`.
- **One-to-one messages.** Message text is sealed on the sender's device and opened on the
  recipient's device. The relay stores the sealed envelope, routing fields and timestamps; it never
  receives message text, a private key or a plaintext record entry.
- **Live presence.** Online now, last seen, typing and read receipts are the four choices from
  v0.0.7, now applied by the relay. A hidden signal is returned as `null` — **not shared** — never
  guessed as offline. Invisible, selected people and hidden people are enforced before a projection
  leaves the server.
- **Connection requests.** Two people must accept before either can send. Requests, pending,
  accepted and blocked states are real relay states, not local labels.
- **Message states.** Queued, sent, delivered and read are reported by the relay and shown in the
  conversation. A queued message survives a dropped connection and is retried when the stream
  returns.
- **Key pinning.** The app remembers the signing and messaging keys of each accepted connection. If
  either key changes, sending stops and the conversation shows a warning instead of trusting the
  new key silently.
- **Account deletion.** Live → Delete live account removes the handle, public keys, consent,
  connections and ciphertext from the relay, then clears the local live data. The private record is
  untouched.

## Encryption, stated precisely

This build is labelled **E2EE alpha** on purpose.

- P-256 ECDH: an ephemeral sender key against the recipient's static messaging key.
- HKDF-SHA256 derives the message key; AES-256-GCM seals the text.
- SHA256withECDSA signs the canonical envelope with the sender's pinned signing key.
- Private keys are generated on the device and wrapped by an AES-256-GCM key held in the Android
  Keystore. They are never sent to the relay.
- The associated data binds the sorted conversation, sender, recipient and client message id.

It is **not** a double ratchet. There is no per-message forward secrecy or post-compromise
security, no multi-device key sharing and no deniable authentication. The primitives are audited
JCA implementations, the composition is deliberately simple and reviewed, and the label says alpha
because that is the honest level of assurance. Messages are retained in the relay for at most 30
days, or until the account is deleted.

## Network permission and what changed

The APK now requests `android.permission.INTERNET` and `ACCESS_NETWORK_STATE`. That is a material
change from v0.0.7, and the release workflow changed with it: it now **requires** `INTERNET`, rejects
an APK with cleartext traffic enabled, and still fails if Play Services, Firebase or a tracking SDK
reaches the `foss` build. Cleartext is disabled by the network security config; only HTTPS/WSS with
system trust anchors is allowed. There is no user-installed CA bypass.

Going live is a choice. The ledger, bank vault, drafts, photos, receipts and contact log remain on
the device and work in airplane mode. The relay sees routing metadata — handle, display name,
public keys, connection state, consent, message size, time and IP — and never the private record.

## Pear / Holepunch companion

The **Pear adapter** ships in this build as two real pieces:

- **Android handoff adapter.** Live → Export Pear handoff writes a JSON file with the record shape
  only: sequence, kind, hash, time, head hash, display name and device model. No subjects, amounts,
  notes, photos, receipts or vault references.
- **Companion node.** [`peer/`](../peer/) is a Node 20+ Pear/Holepunch node built on Hyperswarm and
  Hypercore. It validates the handoff, appends it to a local append-only core and replicates it to
  peers that know the same circle code. Records are deduplicated by a SHA-256 content id.

The node was tested end to end on two local peers over the public DHT: one peer imported a handoff,
the second received and persisted it. The go/no-go decision and the limits are recorded in
[`docs/ADR-pear.md`](../docs/ADR-pear.md). Pear is an independent handoff path, not the authority for
a shared fact and not a second account system.

## Still true

- TLC never holds, moves, pools or escrows money. There is no wallet, no balance, no payment rail
  and no card data. The transfer happens bank to bank; TLC records the evidence you bring back.
- Recognition tokens are signals of appreciation, not currency.
- No Play Services, Firebase, analytics or proprietary SDK in the `foss` build.
- The passphrase remains the only door. There is no fingerprint, face, passkey or device-credential
  unlock anywhere.

## Upgrade notes

- The signing certificate is unchanged (`e04cb8aa…b732c`), so this installs over v0.0.7 without
  losing the local record.
- Presence is still private by default. Nothing is shared until you choose an audience, and going
  live does not change those choices.
- The app does not connect on first launch. Use Live → Go live; the choice is remembered for the
  next unlock.
- A relay operator can see that two handles are connected and when, even though it cannot read the
  message. Use the Pear node when you want a serverless handoff instead.
